# S2：基础 apkg 的实际读取证据与缺口

## 实测

初始合成阶段没有使用、公开或读取第三方牌组内容；没有启动 Anki。后续父审查提供的私有文件计数证据单列于文末。用内存 SQLite 原创构造 `notes(id, flds, tags)`，10 条笔记，以 `\x1f` 分隔字段，再用 fflate 压成 `collection.anki2`。本次 `pnpm exec tsx -e` 测得：SQLite 8192 字节、ZIP 446 字节，读取/清洗 10 条耗时约 1.702 ms。前 5 条输出的正面分别为 word0…word4，背面均为 `meaning\n& red`，tags 为 `["a","b"]`。这只是合成 schema 的读取证据，不是 Anki 兼容性保证。

`apps/web/src/server/services/import-review.test.ts` 的 T1.1 AC8 实际序列化 SQLite 并经过 ZIP、数据库读取、HTML 清洗、事务建卡。AC9 验证新版 marker 与旧版 stub 同时存在时拒绝导入，而不是误读 stub。

## 六个问题的当前结论

1. 检测优先级为 anki21b > anki21 > anki2。未知格式明确拒绝。没有测试导出这些文件的实际 Anki 版本，不列虚构的版本对应关系。
2. 检测到 anki21b 就拒绝，即使同时有 anki2；由合成混合归档测试证明。实际新版是否包含提示笔记，本次没有实文件证据。
3. 未实测 Anki 的“支持旧版”选项，不能声称作者当前版本一定能导出成功。产品给出兼容模式建议，同时提供 CSV 兜底。
4. 实测合成 `notes.flds` 的 `\x1f` 读取。只取前两个字段，不需要 `col.models`/`notetypes` 字段名，不导入媒体、牌组映射或调度。真实版本字段结构仍需导出样本验证。
5. 清洗规则见下表；脚本/style 内容也删除，避免污染文本。不是完整 HTML 解析器，不支持所有命名实体或复杂嵌套 cloze。
6. 使用已存在的 fflate + better-sqlite3；直接从 Buffer 打开内存集合，不解压到用户路径。上传限制现为 64 MiB（CSV/TXT 仍为 20 MiB）、单个集合解压限制 100 MiB，只解压候选集合，忽略媒体。大型文件峰值内存/耗时尚未测量。

## 父审查提供的单一私有文件计数证据

父 agent 本地运行 `readApkgNotes(blank.apkg)` 成功：压缩文件 **39,664,771 字节**、内部数据库 **44,662,784 字节**、**4,028 条笔记**、每条 **9 个字段**。仅记录计数，不复制任何笔记文本；本修复 worker 没有重读、自动导入或公开该牌组。该文件超过原 20 MiB 限制，故上传链路改为 .apkg 64 MiB。没有 Anki 版本、导出选项、兼容/默认各一份新生成导出及大文件峰值内存证据；因此这不是双格式兼容性保证，S2 仍不标完整完成。
