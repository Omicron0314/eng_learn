# T1.4 review_logs 与 events 写入(类型化与查询)

## 目标

把事件写入从“任意 JSON”升级为按类型校验的 API,并提供后续统计依赖的 `review_logs` 查询,保证每次评分正好 1 条复习日志加 1 条事件。

## 范围与非范围

**范围**

- `packages/db/src/events.ts`:为 `docs/specs/README.md` §6 的每个事件类型定义 zod payload schema,导出 `EventType`、`EventPayload<T>`。
- `EventsRepo.append` 改为类型化:`append(tx, userId, type, payload)`,写入前校验 payload,失败抛错(整个事务回滚)。把 T1.2、T1.1 中已有的调用迁移到新 API。
- `EventsRepo` 查询:`listByType(userId, type, range)`、`countDistinctDays(userId, range)`(供 H1 统计)。
- `ReviewLogsRepo` 查询:`countNewIntroduced(userId, range)`、`countReviews(userId, range, { stateBefore? })`、`listBetween(userId, range)`、`firstReviewAfter(cardId, ts)`(供 T6.2)。
- T1.2 的队列计算改用这些查询。

**非范围**:统计页面(T6.3);事件导出。

## 接口

```ts
type EventType = keyof typeof eventSchemas;
type EventPayload<T extends EventType> = z.infer<(typeof eventSchemas)[T]>;
interface EventsRepo {
  append<T extends EventType>(tx: Tx, userId: string, type: T, payload: EventPayload<T>): string;
  listByType<T extends EventType>(userId: string, type: T, range: TimeRange): { id: string; ts: number; payload: EventPayload<T> }[];
  countDistinctDays(userId: string, range: TimeRange, tz: DayConfig): number;
}
type TimeRange = { start: number; end: number };   // [start, end) 毫秒
```

## 验收标准

- AC1:连续评分 N 次(N=10,混合 4 档),`review_logs` 与 `review` 事件各恰好 N 条,cardId 一一对应,事件 payload 中的 `rating`、`stateBefore` 与日志一致。
- AC2:payload 不符合 schema(如 `review` 缺 `rating`)时,`append` 抛错,同事务内的卡片更新与复习日志都回滚。
- AC3:每个事件类型至少有一条合法与一条非法 payload 的测试。
- AC4:`countNewIntroduced` 与 `countReviews` 在跨日界数据上计数正确(含 `dayStartHour`)。
- AC5:`firstReviewAfter` 返回给定时间之后的第一条日志;没有时返回 `null`。
- AC6:`events`、`review_logs` 仍然只能追加(复用 T0.2 的触发器测试,并确认仓储没有暴露更新 / 删除方法:类型测试 `// @ts-expect-error`)。
- AC7:文件库中评分后重启(关闭并重新打开),日志与事件仍在,队列计数不变。

## 测试计划

集成测试使用 `:memory:` 库(AC1–AC6),AC7 使用临时文件。

## 依赖与风险

- 依赖 T1.2。
- 风险:事件 schema 一旦有数据就只能向后兼容地扩展(新增可选字段),不能改字段含义。
