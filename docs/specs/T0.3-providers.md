# T0.3 providers 接口与 Fake 实现

## 目标

定义 LLM、TTS、BlobStore 三个接口,提供真实 LLM 适配器(OpenAI 兼容)、全部 Fake 实现、配置加载,以及统一的结构化输出工具 `completeJson`,让业务代码与测试都不直接接触具体服务商。

## 范围与非范围

**范围**

- 配置:`loadProviderConfig(env)` 用 zod 校验 `docs/specs/README.md` §5 的变量。`LLM_PROVIDER=openai-compatible`(默认)时,`LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL` 缺任何一个都抛 `ConfigError`,错误信息列出所有缺失的变量名;不提供任何默认模型。
- `OpenAICompatibleLLM`:基于 openai SDK,`baseURL`、`apiKey`、`model` 全部来自配置;构造时可注入 `fetch`(测试用)。
- `FakeLLM`:按脚本依次返回预设回复(字符串或抛错),记录收到的每个请求;回复用尽时抛错。
- `completeJson(llm, request, schema, opts)`:
  1. 先以 JSON 模式请求;若适配器报告不支持 JSON 模式,退回纯提示词约束(`jsonModeUsed: false`)。
  2. 解析并用 zod 校验;失败时用 `prompts/json-repair.v1.md` 构造“修复提示”重试 1 次。
  3. 仍失败抛 `LLMOutputInvalidError`(带 zod 错误摘要)。
  4. 每次底层调用(含失败)都通过 `opts.onCall(record)` 回调输出一条 `LLMCallRecord`,由调用方写入 `llm_calls`。
- 成本:配置了 `LLM_PRICE_INPUT_PER_MTOK` 与 `LLM_PRICE_OUTPUT_PER_MTOK` 时计算 `costUsd`,否则为 `null`。
- `TTSProvider` 接口与 `FakeTTS`(返回确定性的静音 WAV,时长与字符数成正比,便于 e2e 播放)。`TTS_PROVIDER=none` 时工厂返回 `null`,前端用浏览器 SpeechSynthesis。
- `BlobStore` 接口,`MemoryBlob` 与 `LocalFileBlob`(根目录 `BLOB_DIR`)。
- 工厂:`createLLM(config)`、`createTTS(config)`、`createBlobStore(config)`。
- 提示词 `prompts/json-repair.v1.md`。

**非范围**:真实 TTS 服务商适配器(待定,作者在 M5 时指定);流式输出;多模型路由。

## 接口

```ts
export type LLMPurpose = "article" | "gloss" | "definition" | "eval";
export type LLMMessage = { role: "system" | "user" | "assistant"; content: string };
export type LLMRequest = {
  purpose: LLMPurpose;
  messages: LLMMessage[];
  jsonMode?: boolean;
  temperature?: number;
  maxTokens?: number;
};
export type LLMResponse = {
  text: string;
  model: string;          // 服务商实际返回的模型名
  tokensIn: number;
  tokensOut: number;
  latencyMs: number;
};
export interface LLMProvider {
  readonly provider: string;   // "openai-compatible" | "fake"
  complete(req: LLMRequest): Promise<LLMResponse>;
}
export class JsonModeUnsupportedError extends Error {}

export type LLMCallRecord = {
  purpose: LLMPurpose; provider: string; model: string;
  tokensIn: number; tokensOut: number; costUsd: number | null; latencyMs: number;
  status: "ok" | "invalid_output" | "error"; error?: string;
};
export function completeJson<T>(
  llm: LLMProvider,
  req: Omit<LLMRequest, "jsonMode">,
  schema: z.ZodType<T>,
  opts: { onCall: (r: LLMCallRecord) => void; price?: Price },
): Promise<{ value: T; model: string; attempts: number; jsonModeUsed: boolean }>;

export interface TTSProvider {
  readonly provider: string;
  readonly voice: string;
  synthesize(req: { text: string }): Promise<{ audio: Uint8Array; mimeType: string; durationS: number | null }>;
}

export interface BlobStore {
  put(key: string, data: Uint8Array, contentType: string): Promise<void>;
  get(key: string): Promise<{ data: Uint8Array; contentType: string } | null>;
  has(key: string): Promise<boolean>;
  delete(key: string): Promise<void>;
}
```

## 验收标准

- AC1:缺少 `LLM_MODEL`(或另外两个变量中任意一个)时 `loadProviderConfig` 抛 `ConfigError`,信息中列出所有缺失的变量名;`LLM_PROVIDER=fake` 时不要求这三个变量。
- AC2:`OpenAICompatibleLLM` 用注入的 fake `fetch` 测试:请求发往配置的 `baseURL`,body 中的 `model` 等于配置值,JSON 模式下带 `response_format: { type: "json_object" }`;返回的 token 数与模型名被正确映射。
- AC3:`completeJson` 首次返回合法 JSON 时,只有 1 次调用、1 条 `ok` 记录。
- AC4:首次返回非法 JSON、修复后合法:2 次调用,第 2 次请求包含修复提示与第 1 次的输出;记录依次为 `invalid_output`、`ok`。
- AC5:两次都非法:抛 `LLMOutputInvalidError`,共 2 条 `invalid_output` 记录。
- AC6:JSON 合法但 zod 校验失败(如缺 `title`)与语法错误走同一修复流程。
- AC7:适配器抛 `JsonModeUnsupportedError` 时自动退回非 JSON 模式重发,`jsonModeUsed` 为 `false`。
- AC8:网络错误或服务商 5xx 产生 1 条 `error` 记录并原样抛出,不做修复重试。
- AC9:配置了单价时 `costUsd = tokensIn/1e6*inPrice + tokensOut/1e6*outPrice`;未配置时为 `null`。
- AC10:`LocalFileBlob` 拒绝包含 `..`、绝对路径或反斜杠的 key;`put` 后 `get` 取回相同字节与 `contentType`。
- AC11:`FakeTTS` 对相同文本返回相同字节;产出的 WAV 能被解析出正确时长。
- AC12:`TTS_PROVIDER=none` 时 `createTTS` 返回 `null`;`TTS_PROVIDER=fake` 时返回 `FakeTTS`;未知值抛 `ConfigError`。

## 测试计划

单元测试全部使用 FakeLLM、fake `fetch` 和临时目录,不发真实网络请求。

## 依赖与风险

**待确认(停下来问人)**

1. **新增依赖**:`openai`(SDK)。
2. **新提示词** `prompts/json-repair.v1.md`(提示词变更需人审),草稿:

```
Your previous reply could not be used: {errors}.
Reply again with JSON only, matching exactly this shape: {shape}.
No markdown fences, no commentary.
```

**风险**

- 不同服务商对 `response_format` 的支持与报错方式不一样,`JsonModeUnsupportedError` 的识别规则要在接入真实服务商时验证(仅以 400 且错误信息涉及 `response_format` 为准)。
- 部分服务商不返回 token 用量,此时记为 0 并在 `error` 字段外另记日志,不影响主流程。
